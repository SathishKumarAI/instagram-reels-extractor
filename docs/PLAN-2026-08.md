# Plan — local-first research platform (2026-08-04)

The requirements document for the next phase. Written after porting the project to
the Windows box and standing up local GPU vision. Everything below is either
**measured on this machine** or marked as an estimate.

Companion docs: `docs/BACKLOG-120.md` (the full feature list), `docs/PRIVACY.md`
(what stays local), `STATUS.md` (where work stopped).

### Hardware budget (the constraint that shapes everything below)
RTX 5070 Ti, **16GB VRAM**, single-user, one workload at a time. Owner's direction:
use it fully. That means the design target is **local-first**, with Claude reserved
for jobs where quality provably matters.

Current VRAM use: `reels-vision` 9.4GB weights + ~2GB KV at 32k ctx ≈ **11.5GB**.
Headroom: ~4.5GB — enough for a small text model *or* a second vision stream, not both.

## 3. Feature specs

### F1 — Discovery pipeline ("find me more reels like these")

**Goal:** stop manually saving reels. The system proposes new ones, you accept or
reject, accepted ones enter the corpus.

**Signals available with your session cookie** (all inbound reads, no posting):
1. Hashtag feeds for the top hashtags in each collection
2. New posts from authors you already saved 2+ reels from
3. IG's own "related/suggested" surface on a reel page
4. Explore feed (already personalised to you)

**Ranking (local, no Claude):** embed candidate caption + hashtags with fastembed →
cosine against the **centroid of each collection** → keep top-N per collection above
a threshold. Dedup against the corpus by shortcode first, then by caption similarity.

**Cost control:** candidates are cheap to *find* and expensive to *process*. So the
pipeline stores only `{shortcode, caption, author, thumbnail_url, score, collection}`
and downloads nothing until you accept. Thumbnails fetched lazily for the UI.

**UI — new `Discover` tab:** card grid, each card shows thumbnail, caption, why it
matched (collection + score + shared hashtags), and Accept / Reject / Snooze.
Accept → appends to that collection's URL list and queues a normal sync.
Reject → remembered, never proposed again.

**Scheduling:** Windows Task Scheduler entry running `reels-scrap discover` nightly,
mirroring the Linux box's `reels-sync.timer`. Jittered start, hard cap on requests.

**Rate limits are the real risk** — `example-profile` already 429s on plain profile lookup.
Requirements: max 1 request / 3-5s, ≤N requests per run, exponential backoff, stop
the whole run on the first 429 and resume next night. Never parallelise IG calls.

**Caveat to state plainly:** automated discovery reads more of Instagram than manual
browsing does. It uses your own session and only reads, but it is closer to the line
of IG's ToS than the current "download what I already saved" flow. Ship it opt-in,
with the request cap visible in the UI.

### F2 — Hashtag chips coloured by saved collection

**Goal:** looking at a tag, know instantly which of your collections it belongs to.

`GET /api/tags` returns, per tag: `{tag, count, collections: [{name, count}]}`.
Colour comes from a stable hash of the collection name into the Catppuccin accent
set, so `ai` is the same colour on every screen. A tag in 2+ collections renders a
split chip (left half / right half) rather than a blended colour — blending would
invent a third meaning.

Applies everywhere chips appear: Tags page, reel cards, reader, search results.
Legend lives in the Tags page header, not repeated per view.

### F3 — Claude vs local, side by side (`Compare` tab)

**Goal:** see, per reel, exactly what you give up by running local.

Schema change: a reel keeps `variants: {backend_name: {summary, facts, tags,
structured, tokens, elapsed_s, cost_usd, model, created_at}}`. The current top-level
fields stay as the "active" variant so nothing downstream breaks.

`POST /api/reels/{id}/compare` runs the reel through both backends and stores both
variants. The tab shows them side by side with a metrics strip (facts, tags, summary
length, seconds, $) and highlights **claims present in one and not the other** —
that difference is the actual decision-making information, not the prose.

Batch mode: run N random reels, aggregate into a scoreboard (avg facts, avg length,
disagreement rate, total cost). That scoreboard is what decides which backend becomes
the default — not intuition.

### F4 — Local-first quality: two-pass extraction — BUILT, MEASURED, NOT DEFAULT

1. **Pass 1 — read:** the VLM transcribes on-screen text per frame.
2. **Pass 2 — structure:** a text-only call turns those readings into the schema.
   Pass 2 never sees the images, so it cannot invent what was not read.

Shipped behind `extract.vision_local_two_pass` (default **off**).

**Measured over 15 reels, same frames, both local:**

| variant | facts | tags | summary chars | structured fields | sec |
|---|---|---|---|---|---|
| 1-pass | 5.53 | 5.20 | 217 | 1.87 | 5.74 |
| 2-pass | **6.47** | 5.07 | 187 | 1.27 | 7.13 |

The hypothesis was "reading and reasoning separately beats doing both at once".
Partly true: +0.94 facts. But summaries got shorter, structured fields got *worse*,
and it costs 24% more time. Not a default. Turn it on when facts-per-reel is the
metric you care about.

**The real find while measuring this** was a formatting bug, not a quality gap:
local models return `structured` nested under the genre (`{"educational": {...}}`)
where Claude returns it flat. Every local record read as "1 field" when it carried
4. `_unwrap_structured()` normalises both shapes — that closed most of the gap the
scoreboard was reporting, for free.

### F5 — Local RAG for Research Chat

Today `/api/chat` answers via Claude. Local path: fastembed retrieval (already
local) → rerank → `qwen3:8b` generates with citations. Keep Claude as an explicit
"deep answer" button rather than the default. Requires VRAM juggling: unload the
vision model between chat calls (`keep_alive` tuning) since 9.4GB + 5GB will not
co-reside comfortably in 16GB.

### F6 — Production readiness

| Area | Requirement |
|---|---|
| Process | API + UI run as background services, restart on failure, start at login |
| Schedule | nightly `sync`, weekly `discover`, both logged and idempotent |
| Health | `/api/health` covers disk, cookie validity, ollama reachability, index freshness |
| Backup | `data/` + `output/` snapshot to `~/vault/`, retention policy |
| Logs | rotate `run.log` (it is append-only and unbounded today) |
| Config | one `config.local.yaml` for machine-specific values, never committed |
| Bootstrap | one script that takes a fresh machine to a working install |
| CI | tests + ruff on push; no secrets in CI |
| Errors | every failure lands in the dead-letter with a reason, surfaced in the Sync tab |

## 4. Sequencing — status 2026-08-04

**Phase 1 — stop the bleeding — ☑ DONE.** utf-8 everywhere (43 sites + stdout),
log rotation, cookie-expiry probe, 429 backoff, carousel skip at enumerate,
`vision_concurrency: 3`, incremental search index (**3m46s → 0.55s**).

**Phase 2 — quality — ☑ DONE.** Compare tab (variants, claim diff, scoreboard) and
two-pass extraction. Two-pass measured worse overall → shipped opt-in, default off.
Found and fixed the `structured` nesting bug that made local look worse than it is.

**Phase 3 — reach — ☑ MOSTLY DONE.** Discover pipeline (budgeted, 429 kill-switch,
27 live candidates) and coloured tag chips (664/1603 tags span 2+ collections).
**Not done:** G8 GPU transcripts (`faster-whisper` + CUDA install), E2 hybrid search.

**Phase 4 — production — ☑ MOSTLY DONE.** `scripts/setup-windows.ps1` (idempotent
bootstrap, `-Schedule` nightly sync + weekly discovery, `-Autostart` API at logon),
rich `/api/health`, CI with tests + ruff + tsc + a secret scan, `docs/SETUP.md`.
**Not done:** F5 local RAG chat, J6 backup/retention, J8 dead-letter UI.

Every phase ended with numbers written into `STATUS.md`. Nothing here is "done"
on vibes — where a hypothesis failed (two-pass), it says so.

### What is deliberately NOT built
- **GPU transcripts (C6/G8)** — needs `faster-whisper` + CUDA/cuDNN on Windows;
  fragile install, and both vision paths currently ignore audio anyway.
- **Local RAG chat (F5/L1)** — needs VRAM juggling: 9.4GB vision + ~5GB text will
  not co-reside comfortably in 16GB. Wants a `keep_alive` strategy first.
- **Epic M (owner requests, 2026-08-04)** — model-provenance badges, per-reel model
  diff in the reader, and collection tags on every reel. Parked in `BACKLOG-120.md`
  by the owner's own instruction: document now, build next session.

## 6. Security posture (this repo is safe to publish)

Verified 2026-08-04:
- `git log --all -- cookies* .env *.session*` → **empty**. No credential was ever committed.
- No credential-shaped value in any tracked file (`[0-9]{6,}%3A…` scan clean).
- `sources.json`, `data/`, `output/`, `reels*.txt`, all media: gitignored. `sources.example.json` is the public stand-in.
- `.githooks/pre-commit` blocks credential filenames, sessionid/API-key values, and reel media — including `git add -f`. Enable per clone: `git config core.hooksPath .githooks`. Tested: blocks a planted sessionid, passes a clean file.

For anyone reproducing this setup, the rule is: **the cookie file is a live login.**
`cookies.txt` grants full access to the Instagram account until logged out. Treat it
like a password — never paste it in chat, an issue, a screenshot, or a log.
Full guidance in `docs/PRIVACY.md`.
